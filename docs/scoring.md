## 五、评审常见追问与我们的回答

提前准备好答案，现场就不会结巴：

1. **「这个和已有的 X 有什么不同？」**
   → 三点。**第一，剧本不是写死的**：一本剧本一个 JSON，丢进 `data/scripts/` 就上线，
   后端对剧本零假设——我们用四本（6/5/6/5 角色）验证过同一套代码都跑得通。
   **第二，Mock 和真实后端共用同一份状态机**（`src/mocks/mockEngine.ts`），Express 的服务层直接调它，
   所以演示的是一个东西、上线的是同一个东西，不存在"两套规则各自漂移"这种 Demo 通病。
   **第三，安全边界在服务端兜死**：真实模式下房间上下文接口的凶手字段恒为 `null`，
   凶手只在 `ended` 状态的结算结果里出现，剧本列表与详情也不下发任何角色的 `secret`——前端改代码也拿不到。

2. **「数据从哪里来？合规吗？」**
   → 剧本全部团队原创，以 JSON 形式随仓库走 MIT 协议，没有爬取、没有第三方数据集。
   玩家侧只存昵称和房间状态，不收集手机号、邮箱或真实身份；房间数据落在本地 `.data/rooms.json`，
   不上传任何第三方。依赖协议逐条核对过（MIT / ISC / Apache-2.0 / BSD-2-Clause，无 GPL/AGPL），
   见 `ATTRIBUTIONS.md`。调 AI 时只发送该玩家**已获得**的线索摘要，不发别人的私密线索和自己的 `secret`。

3. **「如果我一个人用，成本是多少？」**
   → 接近零。静态前端 + 单个 Express 进程，一台 1C1G 的最低配机器就够；存储是 JSON 文件，没有数据库开销。
   唯一的变动成本是 AI：默认 `gpt-4o-mini`，一次提问只带当前房间已公开的线索，量级在千 token 以内；
   **不配 Key 就完全免费**，接口自动降级成本地确定性结果，功能不中断。

4. **「这套东西能扛住多大流量？」**
   → 说实话：不是为高并发设计的。房间状态在单进程内存里，写入是全局串行的（`mutate()` 队列）+
   临时文件改名落盘，适合演示和几十人同时在线的小规模，多实例无法水平扩展。
   但升级路径已经铺好：`prisma/schema.prisma` 按数据模型建好了表，替换面收敛在
   `server/store/roomStore.ts` 一个文件，换 Postgres + 行级锁就能横向扩。

5. **「如果现在给你一周，你会先改哪里？」**
   → 按优先级：① **存储层换 Postgres**，解决水平扩展，替换面已经压到一个文件；
   ② **补鉴权**——现在 `playerId` 由客户端传，知道别人 id 就能冒充，这是当前最大的安全短板，
   必须上服务端会话或 token；③ 断线重连与房间列表（现在只能靠房间码，刷新依赖本地存储）；
   ④ 限流与请求日志；⑤ 剧本内容扩到 8–10 本并做难度分级。
